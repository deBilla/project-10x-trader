02 — Design

System design

One long-running Python process, one Alpaca paper account, a Redis instance for day state and a Mongo collection for the audit trail. The interesting part is not the topology — it is where the boundaries fall.

The shape of it

Four files carry the system: trend_trader.py is the live engine, news.py is the only LLM component, backtest/trend.py holds the strategy shared by live and simulation, and eval/news_replay.py prices the model. Everything else is plumbing or history.

One tick, step by step

The live engine is a single function, TrendTrader.run_tick(), and it reads top to bottom. It fires hourly during market hours.

Step 1 — account and drawdown, before anything else

Equity is fetched, then the drawdown monitor reads today's anchor from Redis, keyed by UTC date. If no anchor exists, this equity becomes it. If equity has fallen past the limit and the switch has not already tripped, it liquidates and latches a pause flag for the rest of the day.

The latch is the important detail: liquidation fires once, not on every subsequent tick. And the liquidation function is injected as a closure scoped to this agent's own symbols, so one agent's kill-switch can never touch another's book.

Step 2 — reconcile, don't re-decide

For each of 30 symbols the engine computes two booleans — want_long from the trend signal, and holding from the broker — and reconciles them. That is the entire decision surface.

Why reconciliation, not events

Because this compares states rather than reacting to transitions, the engine is idempotent. A tick that crashes halfway leaves nothing to repair — the next tick recomputes from scratch and converges. There is no pending-order state machine to corrupt, and no position memory to persist.

The bar the signal is allowed to see

The channel read must use completed sessions only. Alpaca's last 1Day bar is today's partial bar while the market is open, so close.iloc[-1] is the live intraday price — and feeding that to desired_long() turns a daily-close strategy into an intraday one that whipsaws. This shipped, ran for three months, and cost most of the live return before it was caught; completed_bars() now drops the in-progress bar.

The catastrophic stop is the deliberate exception: the backtester checks it intrabar against the bar's low, so reacting to the live price is the matching behaviour there. Only the channel signal needs a closed bar.

Step 3 — sizing, and the cash trap

Target size is 10% of equity, but only cash can be spent. The engine takes the minimum of the two and keeps a 2% buffer, because a market notional order can fill slightly above the quote and without the buffer the last position of the day bounces on insufficient buying power. Anything under $20 is skipped as dust.

Step 4 — journal everything

One Mongo document per tick, carrying every action taken and the want_long / holding / price triple for all 30 symbols. This is what lets you reconstruct why nothing happened on a quiet day, which is most days — a trend system trades rarely by design.

Crucially, each news verdict is journaled alongside the headlines that produced it, the model name, and the prompt version. Without the input, a stored verdict cannot be re-scored against a future prompt, and the production log is useless as an eval corpus.

The trick that makes it all work

desired_long() does not ask "did a breakout happen today". It asks whether the most recent breakout is more recent than the most recent breakdown — a read of current trend state.

entries = close > prior_high
exits   = close < prior_low
last_entry = entries[entries].index.max()
last_exit  = exits[exits].index.max()
in_trend = last_exit is None or last_entry > last_exit

Two consequences fall out, and both are load-bearing.

The live engine needs no memory. Restart it, redeploy it, run it in a fresh container — it recomputes the same answer from history. Nothing to persist, no missed-event risk.

A veto degrades gracefully. Because the answer is a state rather than an event, a block today simply means the engine asks again tomorrow while the trend leg is still alive. A veto delays an entry rather than cancelling it — which is precisely why the eval's cost accounting can be honest. That matters enormously later.

An honest caveat

require_stop_loss: false is not laziness. Fractional equity orders cannot carry Alpaca bracket orders, and on a $1,000 account every position is fractional. There is therefore no resting stop at the broker — exits are managed by the engine on ticks, which means overnight and weekend gap risk is real and unhedged.

Layer 2 — the drawdown kill-switch

Date-keyed in Redis, latching, scoped to one agent's symbols, and asymmetric: it blocks entries while permitting exits. Its known failure mode is documented rather than hidden — change the account balance mid-session and the anchor is stale, so the next tick reads a false drawdown and liquidates. Recovery is manual: clear the anchor and pause keys, then restart.

Layer 3 — the PreToolUse gate

This layer is dormant with the LLM path, but it is the most reusable idea in the repository, because it answers a question every agentic system eventually faces: how do you stop a model taking an action you did not sanction?

The answer is not prompt instructions. It is a hook registered against the tool name that intercepts the call before it reaches the server and can deny it outright.

hooks={"PreToolUse": [
    HookMatcher(matcher="mcp__alpaca__place_.*", hooks=[risk_hook]),
    HookMatcher(matcher="mcp__alpaca__close_.*", hooks=[risk_hook]),
]}

The decision logic behind it, evaluate_order(), is a pure function — no SDK types, no I/O — so it is directly unit-testable, and 14 tests cover it. Its checks run in order: risk-reducing operations always pass; then paused, long-only violation, missing symbol, whitelist, stop-loss present, stop distance, position count, notional resolvable, notional cap. Every decision is recorded with its reason, so a denial is visible after the fact.

Scar tissue worth reading

The first version of the stop-loss extractor only understood a nested stop_loss shape, but the real Alpaca MCP tool uses flat keys like stop_loss_stop_price. The hook therefore denied every bracket order and would have blocked every trade forever. It was caught by the first real order and now has a regression test. The general lesson: a fail-closed gate that misreads its input fails silently and totally.

Deployment

Five Docker services, three of them profile-gated and off by default. The live agent, Redis and Mongo come up on a plain docker compose up -d. The crypto agent, the MCP server and the Mongo web UI each require an explicit profile flag.

The config/ directory is volume-mounted, so parameter tuning is a restart rather than a rebuild. Claude authenticates with a subscription OAuth token rather than an API key, and Compose deliberately blanks ANTHROPIC_API_KEY so a stray key cannot silently override it.
