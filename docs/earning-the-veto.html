Earning the Veto

The trend engine was backtested for four years before it was trusted with a dollar. The language model holding veto power over its entries had never been measured at all. This is the harness that measures it — and what building it taught us about measuring it honestly.

The component nobody measured

The system's governing rule is printed at the top of its README: never trade an unvalidated edge. The daily trend strategy earns its place under that rule — Donchian breakout, regime filter, four years of history, +5.8% expectancy per trade, profit factor 2.82. Every parameter in config/equity/strategy.yaml survived a backtest.

One component never did. Before any breakout entry, NewsSentiment pulls recent headlines, has Claude score them to JSON, and vetoes the entry if the news reads strongly bearish or earnings are imminent. It sits directly in the path of the only validated edge in the system, and it had no backtest, no golden set, no accuracy number — nothing.

The existing test file covered the plumbing thoroughly: tolerant JSON parsing, threshold arithmetic, fail-open behaviour. It covered the model's judgment not at all. That is the hole this harness fills.

Why blocks, not accuracy

The filter can only block. It never initiates a trade — the validated signal stays in charge. That single constraint decides what to measure, because it makes the two error types cost wildly different amounts.

ErrorWhat happensWhat it costs
False positive Blocks an entry the trend signal wanted A trade drawn from a +5.8%-expectancy distribution
False negative Allows an entry it should have stopped Nothing beyond baseline — you are simply unfiltered
The payoff is one-sided, so overall accuracy is the wrong summary statistic. A filter that blocks nothing scores identically to the baseline and costs nothing; a filter that blocks eagerly can only subtract.

So the harness reports block precision: of the entries the filter stopped, what share would actually have lost money. And it reports that number against its own base rate. On a strategy that wins roughly 55% of its trades, blocking at random already lands on a loser about 45% of the time. That, not 50%, is the bar a news filter has to clear to be worth the calls it costs — and it moves with the strategy's win rate, so it is computed per run rather than hard-coded.

The question restated

Not "is the classifier good at reading news." It is: do these specific blocks, on these specific entries, leave the book better off than not blocking at all.

Method: two arms, one simulator

The harness replays history twice and diffs the result. The critical discipline is that both arms run through the same simulator — a reimplementation of the strategy for the filtered arm would let ordinary code drift masquerade as a finding.

Three invariants the harness rests on

Each of these is asserted by a test, because each one silently invalidates every number the harness prints if it breaks.

  • Passing veto=None reproduces the old code path exactly. The deferred retry branch is unreachable without a veto, so the baseline arm is the pre-existing backtest, unchanged. Without this the two arms are not comparable and the diff means nothing.
  • The veto fires at the decision bar's close, not the execution bar. A decision taken at bar i's close executes at bar i+1's open. If the callback ran at the fill, the news window would include the day being traded.
  • A block delays an entry; it does not abandon the leg. Live, desired_long() is a state read — a block today means the agent asks again tomorrow. A simulator that dropped the whole leg on one veto would wildly overstate the filter's cost.

Keeping the future out

The README used to say news was "not cleanly backtestable (lookahead)". That is half right, and the half that is wrong was blocking the most valuable measurement available. Lookahead is fatal when news is an entry signal. For a veto on an entry the price data already generated, the requirement is narrower: every headline the model sees must have been published strictly before the decision.

Daily bars are stamped with the session date, but the decision happens at the close. Using the bar's own timestamp as the window boundary would silently discard the entire trading day's news — the most relevant headlines there are. So the harness maps each bar to its session close and windows backwards from there.

What building it changed

Three design decisions did not survive contact with a running harness. Each was caught by actually executing the thing rather than reasoning about it, and each would have quietly produced a working-looking tool that gave wrong or unaffordable answers.

01

Eager scoring was unaffordable

The first design enumerated every bar a veto could possibly touch and scored them all up front. That set is provably a superset, which felt safe — but it is enormous, because a probe that blocks everything never enters a position and therefore stays "wanting to enter" for every bar of every trend leg.

Scoring is now lazy. Each symbol's simulation runs in a worker thread and hands scoring requests back to the event loop, so only bars the run actually reaches cost an LLM call. The superset probe survives as the pessimistic bound quoted by --plan.

eager 1,094 calls lazy 28 calls on a 6-symbol / 600-day replay
02

The threading fix deadlocked

Making scoring lazy introduced a classic pool starvation. The simulations run in threads and block waiting on scoring futures; the scorer fetches headlines with asyncio.to_thread. Both were drawing from the same default executor, so once every worker was a simulation waiting on a fetch that could not get a thread, the whole run hung — silently, with no output at all.

The simulations now get a dedicated ThreadPoolExecutor, leaving the default pool free for fetches. The regression test is timeout-guarded so a reintroduction fails the suite in 60 seconds instead of hanging CI forever — and it was verified against the broken version to confirm it is not vacuous.

03

The headline number was misleading

The first report showed two numbers that flatly disagreed: attribution summed the blocked winners to a −81% cost, while aggregate expectancy had moved +0.06%. Both were correct.

A veto usually delays an entry rather than cancelling it — the trend signal is re-evaluated the next day, the position opens a bar later, and most of the move is recaptured. Summing the blocked trades' returns therefore describes a cost that never materialised. Every block is now labelled re-entered later or leg abandoned, and the report states outright that the realized price of the filter is the expectancy delta, not the attribution sum.

The cache is the regression signal

Verdicts are cached to disk keyed by symbol · day · lookback · prompt_version · model. Re-running after changing the report, the thresholds, or the attribution logic costs nothing — 0 LLM calls, everything served from disk.

Changing the prompt or the model invalidates every verdict, by design. That is not a cache inefficiency; it is the mechanism that stops a prompt regression from hiding behind stale scores. When you edit _SYSTEM in src/trader/news.py, bump PROMPT_VERSION alongside it.

Real output, real caveats

This is the actual report from a 1,500-day run over 30 symbols with claude-opus-4-8 and prompt v1 — 149 live model calls. Raw figures are committed as eval-news.json; the same numbers are tabulated on the evals page.

Two lines deserve more attention than the expectancy delta. The error count: 111 of 271 consultations failed and failed open, so for a plurality of this run the strategy traded entirely unfiltered — the fail-open decision turned out to matter more than the prompt. And the sample size: 7 of 11 is above the base rate, but at n=11 the probability of doing that well by chance is about 0.17. Suggestive, underpowered, and measured under conditions that flatter the filter.

How to read each block

  • Expectancy delta is the verdict. Everything else is diagnosis. If it is negative, the filter is subtracting from a positive-expectancy distribution and the thresholds need to move.
  • Block precision is read against its base rate, printed beside it. Below the base rate means the blocks are worse than random.
  • Blocked entries are counted once, not once per retry day. A single blocked opportunity re-asks the model every following day while the leg lives; counting those separately would inflate the headline number and dilute precision.
  • Errors fail open and are counted. A fetch failure or a parse failure never blocks a trade — mirroring live behaviour — but it does show up in the activity line, so a broken news feed cannot masquerade as a quiet filter.

What it cannot tell you

Hindsight contamination

The model knows how these dates resolved. It has read about the 2022 drawdown and the 2023 rally. That biases the filter toward looking good on historical replay, which has a useful asymmetry: a poor result is a lower bound on how poor the filter really is, while a good result is not proof of anything. This harness bounds the damage. It does not establish an edge.

Two further limits are worth stating plainly:

  • Alpaca's news archive is not survivorship-clean. Coverage depth for a given ticker in 2021 is not necessarily what a live agent would have received that day.
  • Metrics are per-trade, not portfolio-with-slots. The harness matches the existing backtester's convention, so it does not model the case where a veto frees a position slot that a different symbol then takes. On a 10-slot book that effect is small, but it is not zero.

What this unlocks next

The live path is now instrumented to feed the harness. Every tick's journal entry records the headlines, model, and prompt_version behind each verdict — previously only the verdict itself was stored, which made production history unusable as an eval corpus. Three things follow naturally:

  • A golden set. Roughly 150 labelled headline bundles harvested from the journal, pinned as a CI gate: a prompt or model change that drops block precision fails the build.
  • Threshold calibration. bearish_confidence_min: 0.6 was chosen by feel. With scored history in hand it becomes a sweep — is the model's stated 0.8 actually right eight times in ten?
  • Forward evaluation. The counterfactual replay is contaminated by hindsight; production decisions are not. Joining BLOCKED journal entries to what the symbol subsequently did gives an uncontaminated — if slow — read on the same question.

One structural note for later: the live filter uses the Claude Agent SDK, which spawns a full harness subprocess per call. That is fine at ten calls a day and painful at thousands offline. The Messages API with structured outputs would give schema-guaranteed JSON — deleting the tolerant-parser surface entirely — and batch pricing for offline work. It needs an API key, which the current subscription-token setup deliberately avoids, so the sane split is Agent SDK live, Messages API for evals.
